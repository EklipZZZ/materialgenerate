# 软著第一阶段需求

## 文档目的

本阶段将软著申请信息、生成材料和后续人工补充材料组织成一个可追踪的材料包。目标是先把材料准备流程稳定下来，为后续的官方网页辅助填报预留清晰的数据和接口边界。

## 目标用户

（1）个人独立开发者；

（2）企业或其他单位独立开发者；

（3）多个自然人合作开发团队；

（4）企业/单位与自然人共同作为著作权人的团队。

## 本阶段目标

用户可以在网页中完成以下事情：

（1）填写软件著作权申请信息；

（2）明确录入一个或多个著作权人；

（3）选择原创/修改、权利取得方式和权利范围；

（4）选择单独开发或合作开发；

（5）使用已保存的 LLM 配置补全信息；

（6）生成源代码和用户手册的 DOCX 与 PDF；

（7）查看申请材料清单和材料完成度；

（8）在合作开发场景上传合作开发协议；

（9）记录等待官方系统生成的“申请确认签章页”；

（10）刷新页面或重新登录后继续使用已保存的模型配置和已完成的材料记录。

## 著作权人规则

每个申请可以有多个著作权人，著作权人类型必须由用户明确选择：

### 自然人

需要填写姓名、证件类型、证件号码、国籍、省份、城市和出生日期等信息。

### 企业/单位

需要填写单位名称、单位类别、证件类型、统一社会信用代码或其他证件号码、国籍、省份和城市等信息；首版不采集单位成立日期和园区信息。

### 混合著作权人

企业/单位和自然人可以同时出现在同一申请中。系统不根据参与开发人员自动推断著作权人，所有著作权人都必须由用户主动录入。

旧申请中的 `company_name` 和 `credit_code` 保留兼容：如果历史申请没有结构化著作权人，系统会将旧公司字段映射为一个企业/单位著作权人；新申请以 `copyright_holders` 为主，并继续同步旧字段。

## 开发方式规则

首版页面开放：

（1）单独开发；

（2）合作开发。

数据库和服务端保留：

（1）委托开发；

（2）下达任务开发。

合作开发申请必须有合作开发协议材料。协议由用户自行上传，系统不自动生成、签署或盖章。

## 申请表字段约束

以下长度按字符统计，前端显示实时计数，服务端也会再次校验：

| 字段 | 限制 |
| --- | --- |
| 开发的硬件环境、运行的硬件环境、开发操作系统、软件开发环境工具、运行平台操作系统、软件运行支撑环境 | 每项不超过 50 字符 |
| 编程语言、开发目的、面向领域行业、软件分类 | 每项不超过 50 字符 |
| 软件技术特点 | 不超过 100 字符 |
| 软件的主要功能 | 500～1300 字符；保存草稿时可以暂空，启动最终材料生成前必须满足 |

申请人、申请人地址、邮政编码、联系人、联系电话和联系邮箱为可选信息，不由 AI 猜测或代填。软件分类、面向领域/行业和编程语言提供常用选项，同时允许自定义填写。

## 源码核对反馈

申请信息保存后，用户可以上传 ZIP、TAR.GZ 或 TGZ 源码压缩包。系统会：

（1）安全解压并统计实际读取到的源代码文件和行数；

（2）结合源码和当前技术字段生成修正建议；

（3）展示原值、建议值和依据，由用户勾选后写回当前表单草稿；

（4）用户检查并保存后，建议才成为申请数据。

源码压缩包只作为一次性分析输入，分析完成后删除临时对象。著作权人、证件、权利、申请人和联系人等信息不会由源码反馈自动修改。

## 材料规则

首版核心材料包括：

（1）源代码 DOCX；

（2）源代码 PDF；

（3）用户手册 DOCX；

（4）用户手册 PDF；

（5）合作开发协议（仅合作开发时必需）；

（6）申请确认签章页（等待官方系统生成，用户签章后上传）。

申请确认签章页不能由本系统自行制作。系统只维护其“等待官方系统生成”或“已上传”等状态。

身份证明、委托开发协议和下达任务证明材料作为条件材料预留，不在首版普通独立开发流程中强制阻塞文档生成。

## 用户主流程

```text
新建申请
  → 选择并录入著作权人
  → 填写软件及权利信息
  → 选择开发方式
  → 保存申请
  → 可选：AI 补全
  → 上传源码压缩包
  → 查看源码核对建议并由用户确认写回
  → 生成 DOCX/PDF 材料
  → 上传条件材料
  → 查看材料完整度
  → 进入官方系统获取签章页并人工签章
  → 上传签章页
```

## 明确不在本阶段

（1）专利模块和专利文书生成；

（2）官方版权登记网站的自动登录、自动填表和自动提交；

（3）自动生成或伪造签名、印章和合作开发协议；

（4）真正脱离前台请求的云端后台任务队列；

（5）Pydantic Python 数据模型体系。

## 验收标准

### 申请人场景

（1）个人申请可以填写身份证信息，不要求统一社会信用代码；

（2）企业/单位申请可以填写单位类别和统一社会信用代码；

（3）多个个人可以作为合作开发著作权人；

（4）企业/单位和个人可以混合录入；

（5）旧的公司字段申请可以正常读取、编辑和生成材料；

（6）申请人、地址、联系人和联系方式可以留空，不由 AI 猜测；

（7）委托开发、下达任务值可以被服务端识别，即使首版页面不开放。

### 材料场景

（1）一次生成同时产生源代码和用户手册的 DOCX/PDF；

（2）合作协议可以上传、替换和删除；

（3）缺少合作协议时，合作开发申请显示未完成；

（4）签章页显示“等待官方系统生成”；

（5）上传签章页 PDF 后状态变为“已上传”；

（6）不同用户不能读取或下载他人的申请和材料。

### 配置和任务场景

（1）LLM API Key 保存后不会因刷新或重新登录而要求再次输入；

（2）前端、日志和接口响应不出现完整 API Key；

（3）同一申请不能同时创建两个运行中的生成任务；

（4）任务失败后可以重新生成；

（5）生成记录、任务状态和材料状态能够相互对应。
